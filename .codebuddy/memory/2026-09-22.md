## VN 模式双击/长按不触发 TTS 朗读 —— 根因与修复 (codex/reader-tts-read-aloud)

- 现象：用户已开启 设置→行为→双击=“朗读并翻译句子”，分页/连续模式双击能开始 TTS，但 VN 模式不行。
- 真正根因（与最初的猜测无关）：`app/src/main/assets/hoshi-web/reader/reader-translation.js` 的 `collectCandidateElements()` 只扫描 `document.body.children` 收集独立块段落（如 EPUB 常见的 `<div>` 段落）。分页/连续正文较平铺（段落是 body 直接子节点），能收到；但 **VN 正文深层嵌套** `body > stage > screen > content > div.paragraph`，`document.body.children` 只见到 `stage`，嵌套 `<div>` 段落从未被收集。
  - 后果：`collectVisibleTargets()` 返回空队列 → `startReadAloudFromPoint` 直接 return；同时 `targetAtPoint` 的 `closest('[data-hoshi-...]')` 也因 `assignTargetIds()` 没给这些 div 赋值而返回 null → 命中失败 → 不朗读。仅 `<p>` 书能用，纯 `<div>` 段落书 VN 完全失效。
- 修复：把 `collectCandidateElements` 改为递归 `walkStandaloneBlocks(root, collected)`，遍历 body 所有后代块：
  - 含 `TARGET_SELECTOR` 后代的容器 → 递归（已由其内 p/li 等收集）；
  - 自身是独立块且内部无更细独立块后代 → 收集；
  - 否则递归。新增辅助 `standaloneBlockDescendantExists`。避免把多段合并成一段、避免与 querySelectorAll 重复收集。
  - 同时回退了初版误加的 `runSentenceAction(forceReadAloud)` 改动——真实修复在 JS 收集逻辑，VN 应与其他模式一致受同一开关控制。
- 验证：JS `node --check` 通过；`reader-translation.test.mjs`（8/8）与 `reader-visual-novel.test.mjs`（86/86）全绿；`:app:compileDebugKotlin` BUILD SUCCESSFUL。
- 该递归修复对分页/连续模式下深层嵌套 EPUB 同样有益（之前若 div 段落不是 body 直接子节点也会漏）。

## 系统引擎（MultiTTS）语速滑块没反应 —— 修复

- 现象：用户用「系统引擎」下选的具体引擎 MultiTTS，有声但朗读设置语速滑块调了快慢完全没变化。
- 根因：MultiTTS 这类第三方系统 TTS 引擎忽略对象级 `TextToSpeech.setSpeechRate()`；而 `SystemReadAloudEngine` 原本只靠 `setSpeechRate()` 下发语速。
- 修复：`SystemReadAloudEngine.speak()` 的 params 里额外 `putFloat("rate", speechRate)`（framework key 即字符串 `"rate"`，不引用可能隐藏的 `KEY_PARAM_RATE` 常量避免编译失败）；`speak()` 读实时 `speechRate` 字段，使滑块在下一句即生效、无需重启。对象级 `setSpeechRate()` 保留（Google 默认引擎仍认）。
- 风险：若某引擎连 per-utterance `"rate"` 也不吃，应用层无标准解法，只能去该引擎自己的 App 设语速。已装机（设备 381QYGEM226CZ）待用户验证。

## VN 朗读不工作 —— 真正的根因（一）：VN 模板漏注入 reader-translation.js

- 现象：分页/连续模式双击能朗读，VN 模式双击只弹"整句翻译"卡片、TTS 不响；VN 里工具栏朗读按钮同样无效。
- 根因：`app/src/main/assets/hoshi-web/reader/reader-visual-novel.js` 模板里**没有** `__HOSHI_READER_TRANSLATION_SCRIPT__` 占位符（paginated/continuous 都有），而 `ReaderPaginationScripts.shellScriptWithRestoreToken` 只做字符串替换 → VN 页面根本没注入 `reader-translation.js` → `window.hoshiReaderPageTranslation` 不存在 → `targetAtPoint`/`collectVisibleTargets`/`collectTargetsAfter` 全返回 undefined。Kotlin 侧 `targetAtPoint` 回调拿到字面 `"null"` → `hit == null` → `startReadAloudFromLongPressPoint` 直接 return，TTS 永不启动。`git log -S` 显示该占位符从未出现在 VN 模板里，属遗漏而非故意移除。
- 修复：给 VN 模板补上 `__HOSHI_READER_TRANSLATION_SCRIPT__`（放在 layout semantics 之后、VN content stream 之前），并在 `app/src/test/js/reader-visual-novel.test.mjs` 的 `readerSource()`/`configuredReaderSource()` 里补对应 `.replaceAll`，否则该测试文件会 `ReferenceError: __HOSHI_READER_TRANSLATION_SCRIPT__ is not defined`。

## VN 朗读不工作 —— 根因（二）：extractTargetText 去标点导致朗读队列无法切句

- 现象（用户后半段反馈）：VN 里"上一句/下一句"没反应。
- 根因：`reader-translation.js` 的 `extractTargetText` 调了 `global.hoshiReader.normalizeText`（= `reader-text-semantics.js` 的"只保留可计数字符"正则），把 `。、！？「」` 全删掉。朗读队列 `readAloudQueueItems` → `ReadAloudSentences.split` 靠 `。．！？!?` 断句，输入没有标点 → 每段只剩 1 个朗读单元。VN 一屏 = 一段 → 队列长度 1 → `skipNext` 走到 `next >= items.size` 直接 `stop()`，`skipPrevious` 回到同一段 → "没反应"。分页/连续一页多段，所以只是粒度退化不明显。

## VN「上一句/下一句」没反应的真正解法（commit 23c96e2 之前最后一轮）

- 修标点后实测：VN 朗读队列 `size` 仍是 **1**，因为 VN 一屏就是**一句**（`visualNovelSentencesPerScreen=1`，block 模式下一个顶层块 = 一屏）。队列只有 1 个单元 → `skipNext` 走到 `next>=size` → `stop()`，`skipPrevious` 回同一段 → "没反应"。这是 VN 特有的。

## 音量键朗读"不切句"真正根因与修复（在 9084875 基础上）

- 现象（用户实测）：朗读播放时按音量键仍不切句。
- 定位过程：在 3 个文件加临时 `Log.w("HoshiVKey",...)`（Meizu 上 Log.d 被过滤，见上）+ JS `dbgDom` 桩，build+install 到 Meizu 381QYGEM226CZ，用 `adb shell input keyevent 24/25` 模拟音量键 + `adb logcat -s HoshiVKey` 抓日志。关键日志证实 **dispatch+handler 链路本身是通的**：
  `volumeKeyResult keyCode=24 readAloudActive=true action=ReadAloudSentenceNavigation(direction=Next)` + `dispatchKeyEvent ... consumed=true`。即 readAloudActive=true 时音量键正确路由到切句且被消费。
- 真正根因（模式相关）：`ReaderWebView.kt` 里 **key handler 的 `ReadAloudSentenceNavigation` 分支直接调 `skipPrevious()/skipNext()`，但漏掉了 `23c96e2` 给底部播放条做的 VN 单句屏按屏跳逻辑**。VN 一屏=一句话 → 朗读队列 size=1 → `skipNext()` 走到 `next>=items.size` 直接 `stop()`，于是 VN 里按音量"下一句"是**停掉朗读**而非翻屏，表现为"不切句"。分页/连续模式一页多句，所以当时实跑的分页书测试链路是通的，掩盖了该 bug。

## 修复：VN 朗读时正文重复显示（用户截图「这个有没有解决」）

- 现象（用户截图）：VN 阅读页 + 朗读播放条（⏮⏸⏭ + 字数进度）时，段落文字出现两份：先完整一句，紧接着同一句的前半段再出现一次，且重复的那份正好被朗读"当前句"高亮（深琥珀）覆盖；整块外层是朗读"当前段"浅琥珀底色 —— 说明两份文字在**同一个段落元素**内。
- 根因：VN 逐字显示（reveal）与朗读高亮互相踩：
  1. `reader-visual-novel.js` 的 `prepareTextNodeForReveal` 把一个文本节点换成 `[visible 文本节点][hidden span(data-hoshi-visual-novel-unrevealed, visibility:hidden)]`，`revealOneCharacter` 每次 tick 都重写 `segment.visible.textContent = chars.slice(0, revealed)`；hidden 文本仍在 DOM 中。
  2. `reader-translation.js` 的 `_findSentenceRange`/`_wrapRange` 把 hidden 的文本一起算进段落"原文"，并且会把 visible 文本节点切开、把其中一段移进 `.hoshi-read-aloud-sentence` span。
  3. 之后 reveal 的 tick / `completeCurrentReveal` 继续往 `segment.visible` 写 `slice(0, revealed)`，被移进高亮 span 的字符又在原位写了一遍 → 屏幕上该字符序列重复（重复部分恰好落在高亮 span 内，与截图完全吻合）。而 `clearReadAloudHighlight` 只 `classList.remove`，从不还原被切开的 DOM，于是副本一直残留、`_findSentenceRange` 的 baseText 还会把副本算进去导致后续句子定位错位。
- 修复（只改 `app/src/main/assets/hoshi-web/reader/reader-translation.js`）：
  1. 新增 `isUnrevealedTextNode(node)`，`_findSentenceRange` 与 `_wrapRange` 的文本遍历都跳过 `[data-hoshi-visual-novel-unrevealed]` 内的文本（VN 自己的 `isUnrevealedTextNode` 同样语义）。
  2. 新增 `completePendingVisualNovelReveal(element)`：高亮前若段落里还有未显示 span，就调 `window.hoshiReader.completeCurrentReveal()` 把逐字显示补完（与 `reader-visual-novel.js` 里 sasayaki 高亮的既有做法一致 —— 现有测试 `visual novel Sasayaki completes reveal before highlighting the active cue` 就是这个模式），保证一个段落只有一份文本节点。`highlightReadAloudSentence` 在找到段落后先调用它。
  3. `clearReadAloudHighlight` 改为 **unwrap** `.hoshi-read-aloud-sentence` span（新增 `unwrapElement`），不再只去 class；避免反复包裹残留副本。（故意不调 `parent.normalize()`：VN reveal 的 `visible` 是空文本节点，normalize 会把它删掉从而打断 reveal。）
- 验证：`node --check` 通过；`reader-translation.test.mjs` 8/8、`reader-visual-novel.test.mjs` 88/88 全绿；`scripts\install.ps1` 装机成功并确认 APK 内 `assets/hoshi-web/reader/reader-translation.js` 含 `completePendingVisualNovelReveal`/`unwrapElement`/`isUnrevealedTextNode`。
- 待办（未做，本机 shim 不支持）：给 `reader-visual-novel.test.mjs` 补"朗读高亮前会补完 reveal、反复高亮+清除后段落文本不重复"的用例——该文件 DOM shim 目前缺 `splitText`/`intersectsNode`/`commonAncestorContainer`，`_wrapRange` 在 shim 里跑不了，要先用测试脚手架补这三个 DOM 行为。

## 修复：调"VN 文字背景颜色"却整页变黑（用户反馈）

- 现象：用户开启 VN 相关设置后，调「VN 文字背景颜色」，感觉**整个页面变黑**。
- 真正根因（与文字背景无关）：整页黑来自**「VN 背景」（整体背景）的默认值纯黑 `0xFF000000`**。`ReaderSettings.backgroundColor()` 在 `viewMode==VisualNovel && vnBackgroundEnabled` 时无条件返回 `vnBackgroundColor`，铺满整个 `.hoshi-vn-stage`（stage 全屏）。只要「VN 背景」开关开着且没选过颜色，整页就是纯黑。用户调的「VN 文字背景」只包住 `.hoshi-vn-content`（flex 居中、内容尺寸，绝不铺满整页），不是元凶。两个开关名接近，用户误以为是同一个。
- 修复（`ReaderSettings.kt` + `ReaderAppearanceView.kt`）：
  1. `vnBackgroundColor` 默认值 `0xFF000000` → `0x00000000`（透明/未选），主数据类与 `ProfileReaderAppearanceSettings` 两处都改。
  2. `backgroundColor()`：`viewMode==VisualNovel && vnBackgroundEnabled` 分支里，仅当 `vnBackgroundColor.readerColorAlpha() != 0` 才 return 该色；否则**继续走主题/显示设置背景**（不再空白/纯黑）。
  3. 迁移：legacy `from` 与 DataStore `toReaderSettings` 读取时，若精确等于旧默认 `0xFF000000L` 视为"未选"→ 转 `0x00000000`。这样用户设备上已写入的纯黑默认值升级后即不再整页黑（极少数"特意选了纯黑"的用户会被重置为未选、可重选）。
  4. 取色器「重置」`defaultColor` 由 `0xFF000000` 改为 `0x00000000`，避免重置又制造黑屏。
- 验证：`:app:compileDebugKotlin` BUILD SUCCESSFUL。CHANGELOG `[Unreleased]` 该 Added 条目补了"默认不再纯黑、未选回退主题、迁移旧黑"。
- 给用户的话：想要"文字底板"但不整页黑时，关掉「VN 背景」开关、只开「VN 文字背景」即可；要整页纯色背景再开「VN 背景」并主动选色。
- **durable 提醒**：这种"某开关默认值在开启时直接铺满整页且颜色刺眼"是坏默认，加类似开关时默认应透明/回退而非纯黑。

## 修复：调"VN 背景颜色"把整张背景图片(壁纸)盖掉 + 设置项命名混淆（用户反馈）

- 现象：用户只想调"文字底板（图里绿框那块）"的颜色，但一改设置整张壁纸就变。
- 真根因（CSS 分层缺陷）：VN 模式下 `--hoshi-background-color` 被画了**两层**——`ReaderContentStyles.kt` 的 VN 分支给 `html, body` 设了 `background: var(--hoshi-background-color) !important`（line 257），而 `reader.css` 的 `.hoshi-vn-stage` 又设了 `background: var(--hoshi-background-color)`（line 154），`.hoshi-vn-screen { background: inherit }` 再继承一层。**壁纸图片 `background-image: var(--hoshi-vn-background-image)` 挂在 `html, body` 上**（ReaderContentStyles line 366-371，全局追加），但 `.hoshi-vn-stage` 位于 `html/body` 之上、又用不透明纯色铺满 → 纯色**盖住**壁纸。所以用户改"VN 背景颜色"→ `--hoshi-background-color` 变不透明 → 壁纸被盖 → "整个壁纸都变了"。

- 修复：
  1. `reader.css` 的 `.hoshi-vn-stage` 背景改为 `background: transparent`，页面背景色/图统一由 `html, body` 提供（颜色作 `background-color` 兜底、图作 `background-image` 覆盖其上）。这样**有壁纸时壁纸恒可见，调背景色不再盖没壁纸**；`.hoshi-vn-screen { background: inherit }` 随之变透明。
  2. 文案改名（中英双语）：`VN 背景颜色`→`VN 页面背景色` / `VN Page Background Color`；`VN 文字背景`→`VN 文字底板` / `VN Text Panel`；`VN 文字背景颜色`→`VN 文字底板颜色` / `VN Text Panel Color`。
