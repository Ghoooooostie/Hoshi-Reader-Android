## E-ink tap lookup — CORRECTED fix (supersedes 2026-09-13 note)
The 2026-09-13 "real fix" (adding `body { user-select: none }` in
`app/src/main/assets/hoshi-web/reader/reader.css`) was WRONG and made things worse: with
`user-select: none` on `body`, Chrome's `document.caretPositionFromPoint()` (used by
`hoshi-web/shared/selection.js` `getCaretRange`, the first branch in Chrome) returns **null**, so
`selectAt → SelectText` finds no word and the lookup silently does nothing. That is why "加了 CSS 还是点不动".

True root cause of the E-ink slow-tap problem: Chromium's *internal* long-press timer (independent of
Android `isLongClickable`/OnLongClickListener) fires on a slow E-ink tap, starts a native text-selection
**action mode**, which makes `HoshiReaderWebView.isNativeSelectionActionModeActive()` true, and
`shouldIgnoreReaderGestureEvent` then swallows the app's `onTap` (word lookup).

Final fix (branch `codex/reader-own-tap-longpress`, uncommitted):
- `ReaderChapterWebView.kt` `HoshiReaderWebView.startActionMode(...)` now returns `null` (both
  overloads) so Chromium's native selection action mode never starts — no shadowing of taps, and the
  app's JS-driven selection (`window.hoshiSelection.*` + CSS Custom Highlights) is the only path.
  Removed the now-dead `ReaderHighlightActionModeCallback` class. Native highlight menu is gone, but
  highlight is still available via the app's own JS popups (`highlightReaderPopupSelection` →
  `hoshiReaderPopupHost.highlightSelection`); word/sentence selection popups are JS-driven.
- Reverted `reader.css` `body { user-select:none }` so `caretPositionFromPoint` works again.

Build/install verified: `assembleDebug` succeeds, APK installed to E-ink `S101022210032`. **On-device
E-ink tap-lookup + long-press-sentence verification still pending user report.**

## Tap lookup: gesture chain is FIXED — remaining bug is POPUP VISIBILITY (root cause found)
On-device logcat proved the tap→lookup chain works end to end on E-ink (so the action-mode fix above
did its job):
`Swipe UP result=Tap` → `selectAt` → `selectAt result nothing=false` → JS bridge
`HoshiTextSelection.postMessage` fires → `handleTextSelected` runs → `lookupRootPopup` returns
**non-null** (`lookupNull=false`, word e.g. `ち着いた`). So selection + dictionary lookup are fine.

The popup is nevertheless INVISIBLE. Root cause chain:
- Lookup popup is NOT an Android window — it is an in-WebView iframe overlay:
  `ReaderLookupPopupLayer.kt ReaderLookupPopupIframeSync` → `window.hoshiReaderPopupHost.renderStack()`
  (`hoshi-web/popup/reader-popup-host.js`), which creates `.hoshi-reader-popup-shell` +
  `.hoshi-reader-popup-iframe` (src `https://appassets.androidplatform.net/popup/iframe.html?v=...`,
  served via `shouldInterceptRequest`).
- That host's injected CSS gates visibility:
  `.hoshi-reader-popup-shell { visibility:hidden; opacity:0 }` and only
  `.hoshi-reader-popup-shell[data-content-ready="true"][data-reveal-ready="true"] { visibility:visible }`.
- `data-content-ready` is set true ONLY when the iframe postMessages `{source:'hoshi-popup-iframe',
  name:'contentReady'}` to the parent (`reader-popup-host.js` listener; origin check
  `event.origin !== 'https://appassets.androidplatform.net'` is *not* the problem — origin logs correct).
- On E-ink: iframe loads fine (`readyState:"complete"`, `bodyLen:8275`, correct href),
  `data-reveal-ready` reaches `"true"`, but the parent only ever receives `shellReady` / `scrollState`
  messages — **never `contentReady`** → `data-content-ready` stays `"false"` → popup stays hidden.
  (`contentReady` is posted from popup.js via `window.hoshiPopupObserveContentReady?.()` during entry
  rendering; entry rendering apparently never completes on E-ink — likely the
  `webkit.messageHandlers.getEntry`-style bridge path. Not yet root-caused.)
Next step: find why `contentReady` is never posted (popup.js entry-render path / `hoshiPopupObserveContentReady`
definition), rather than touching the gesture layer again.

## ROOT CAUSE FOUND & FIXED: popup.js used `??=`, unsupported by the E-ink WebView
The E-ink device's WebView is an OLDER Chromium: it supports `?.` / `??` (Chrome 80+) but **NOT the
logical-assignment operators `??=` / `||=` / `&&=` (Chrome 85+)**.
`hoshi-web/popup/popup.js` used `??=` twice → the whole file threw
`Uncaught SyntaxError: Unexpected token '='` at parse time → **zero lines of popup.js ran** →
`window.renderPopup` (assigned at popup.js:1904) stayed `undefined` → dictionary entries never rendered
→ `.entry .glossary-content` never appeared → `contentReady` never postMessaged →
`.hoshi-reader-popup-shell` kept `data-content-ready="false"` → CSS `visibility:hidden` → invisible popup.
(Tell-tale follow-on error also seen: `closeOverlay is not defined`, since it lives in popup.js.)
Note `shellReady` / `scrollState` still worked because they come from the *inline* scripts in
`LookupPopupHtml.kt`, not popup.js — which is why the iframe looked "loaded and alive" while broken.

FIX (in `app/src/main/assets/hoshi-web/popup/popup.js`): replaced both `??=` with plain `??`:
- `window.lookupEntries ??= [];` → `window.lookupEntries = window.lookupEntries ?? [];`
- `(grouped[g.dictionary] ??= []).push({` → `(grouped[g.dictionary] = grouped[g.dictionary] ?? []).push({`
Verified: after the fix, logcat shows **no** `SyntaxError` and no `closeOverlay is not defined`.

General rule for this project: the E-ink WebView ≈ Chrome 80-84. Avoid `??=`/`||=`/`&&=` and other
Chrome>84 syntax (incl. runtime APIs like `replaceAll`, `Array.at`, `structuredClone`) in any JS shipped
in `app/src/main/assets/hoshi-web/**` or generated from Kotlin templates.
