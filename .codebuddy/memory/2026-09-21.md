## 排查：查词/AI 弹窗"白色背景"来源
- 用户问：长按后点击触发自动查词（截图是 AI 单词分析卡片，含"词性/作用/补充"，见 `AdvancedAiSettings` LEGACY_WORD_PROMPTS），
  弹窗后面有一大块白色背景。
- 根因（均为**预存在**代码，非本次手势改动引入；本次 diff 未触碰这两个文件）：
  1. 阅读器弹窗是原生注入到阅读 WebView 的浮层 `#hoshi-reader-popup-layer`，
     `app/src/main/assets/hoshi-web/popup/reader-popup-host.js` 里 `.hoshi-reader-popup-shell` 写死 `background:#fff`，
     仅当 `data-dark-mode="true"` 才变 `#000`（`applyShellStyle` 用 payload.darkMode，即 `ReaderSettings.usesDarkInterface`）。
  2. iframe 文档 `popup.css` 里 `html,body{background-color:transparent}`，`.advanced-ai-card{background:transparent}`，
     所以 AI 卡片本身不画底色 —— 看到的白色就是 shell 的底。
  3. shell 尺寸 = `LookupPopupLayout.calculate()` 算出的弹窗框（width/height 取用户"弹窗尺寸"设置，默认 320x250；
     AI-only 时 maxHeight 压到 `AdvancedAiCompactPopupMaxHeightDp=184`），**不按内容收缩**，且 iframe 透明，
     内容短就露出一大块 shell 白底。
- 可选修法（待用户选）：A) 让 shell 底色跟随阅读背景色；B) iframe 上报内容高度、shell 收缩到内容；
  C) 维持现状（浅色主题下白底即设计如此）。
- **用户对照 demo（Hoshi-Reader-Android_demo 的系统"翻译→选这个软件"即 ProcessTextLookupActivity 弹窗）确认要 B**。
  根因补充：阅读器内弹窗高度默认 `popupWidth/popupHeight=500`（ReaderSettings），且竖排书 `LookupPopupLayout.height()`
  恒取 `min(availableHeight, maxHeight)`——不管内容多短都撑满 → 大片空白白底。demo 侧 shell CSS 相同（#fff），
  只是内容恰好填满所以看着正常。
- 已实现"弹窗按内容收缩"（只动 JS/HTML 模板，不动原生桥）：
  1. `LookupPopupHtml.kt`：消息桥新增 `contentHeight` handler；底部脚本新增 `postContentHeight()`
     （用 `body.getBoundingClientRect().height`，兜底 scrollHeight）+ ResizeObserver 跟踪 entries-container；
     `postReady()` 先发 contentHeight 再发 contentReady（postMessage 保序，保证收缩发生在显示前）。
  2. `reader-popup-host.js`：`applyContentHeight(record, h)` 把 shell 收缩到 `frameContentTop + min(h, frame.height - top)`，
     iframe 高度同步为 next；`contentHeight` 消息在宿主拦截 **return，不上报原生**（原生桥无需改）；
     `needsRender`/`parkRootRecord` 时清 `record.contentHeight`，重渲染时复用缓存高度（注意：不能按值相等早退，
     必须比对 shell.style.height，否则重渲染后恢复不回去——已被测试抓出）。
     `dictionary-search-root` 跳过收缩。
  3. 测试：`reader-popup-host.test.mjs` 新增 5 例（收缩/夹紧/双 bar 偏移/重渲染保持/内容替换重置），33 例全过；
     selection.test.mjs 34 例全过。`assembleDebug` 通过，已 `adb install -r` 并冷启动。

## 修复：朗读"查词自动暂停"在连续查词时的竞态漏洞（承接上方"朗读播放时点击查词自动暂停"）
- 复现：朗读播放中，先点词查词（正确暂停）→ 弹窗未关再点另一个词。此时 `handleTextSelected` 开头的
  `setLookupPopups(emptyList())` 会把"因查词暂停"的标记消费掉并触发 `readAloudViewModel.resume()`
  （异步，`ReadAloudController.playFrom` 里 `isPlaying=true` 在 requestAudioFocus/prepareEngine 之后才置位），
  紧接着的 `pauseReadAloudForLookupIfNeeded()` 读到 `isPlaying==false` → 漏暂停，朗读在弹窗打开时继续播放。
- 修法（不改 `setLookupPopups` 签名，避免破坏既有单测的尾随 lambda 绑定，如 `setLookupPopups(emptyList()) { }`）：
  `ReaderWebView.handleTextSelected` 打开发新弹窗时**不再先清空弹窗**，直接 `setLookupPopups(listOf(popup))` 替换旧弹窗
  （`setLookupPopups` 内部本就会按 activeIds 过滤掉旧 popup 的历史/模式，等价）；仅当 `lookup == null`（取消选择）分支
  才 `setLookupPopups(emptyList())` 以清空并恢复播放。这样暂停标记能保留到弹窗真正关闭时才恢复。
- 曾尝试的做法：给 state holder / ReaderWebView 的 `setLookupPopups` 加 `resumePausedPlayback: Boolean = true` 末位参数，
  会与 `ReaderWebViewStateHolderTest` 的尾随 lambda 用法冲突（尾随 lambda 绑定最后一个参数，Boolean 不是函数类型 → 编译错），已回退。
- 已完成（2026-09-21 收尾）：`handleSentenceLongPressed`（长按句子 AI 卡）已用同法修好——
  移除开头的 `setLookupPopups(emptyList())` 预清空，改为在 `readerAiRootPopup` 之后调用
  `pauseSasayakiForLookupIfNeeded()` + `pauseReadAloudForLookupIfNeeded()`，再用 `setLookupPopups(listOf(popup))`
  替换旧弹窗（关闭时统一恢复）。`:app:ReaderWebView.kt` IDE 诊断 0 error。
- 仍潜在但本次不改：`handlePageTranslationLongPressed`（整页翻译）仍是先 `setLookupPopups(emptyList())` 写法，
  但它是触发整页翻译请求、并非停留型弹窗，竞态影响不同，已向用户说明待定。

## 修复：朗读播放时点击空白关闭查词弹窗卡顿
- 复现：朗读播放中查词（弹出词典弹窗）后，点击空白处关闭弹窗要卡顿很久。
- 根因：`ReaderChapterWebView.kt` 的 `onTap` 在关闭弹窗前先执行 `selectAt()` —— 对阅读 WebView 做一次异步 JS 选词检测
  （`evaluateJavascript(ReaderSelectionCommand.SelectText)`），回调里 `selectedNothing` 才关闭弹窗。朗读播放时 WebView 正忙于
  `highlightReadAloudTarget(reveal=true)` 高亮+滚动当前句，该 JS 被排队延迟，弹窗迟迟不消失 = 卡顿感。
- 修法：两个 `onTap`（Continuous 与 Paginated/VisualNovel）在 `currentReaderPopupFrames.value.isNotEmpty()`（弹窗已开）时
  直接 `onReaderTapOutside()` 关闭弹窗，跳过 `selectAt` 的 JS 选词检测；弹窗未开时仍走原 `selectAt` 逻辑。
  行为变化：弹窗打开时点击空白直接关闭，不再先尝试在点击处查新词（避免与延迟 JS 竞争）。
- 顺带修复今天 WIP 引入的 2 个编译错误（否则分支无法 `compileDebugKotlin`）：
  `AdvancedAiSettingsView.kt` 的 `CollapsibleSection` 用 `Surface`/`Spacer` 但缺 import；
  `ReaderWebView.kt` 的 `resumeReadAloudAfterPageTranslationIfNeeded`（局部函数）被 `clearReaderPageTranslations` 在定义前调用（前向引用），已前移到调用点之前。
