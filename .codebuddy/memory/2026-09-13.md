## E-ink tap lookup (reader) — CORRECTED root cause + fix
User report: single-tap dictionary lookup works on a phone but not on an E-ink device, same app/book.
The earlier "hardcoded 500 ms window / 12 px slop" theory was WRONG (user pushed back, correctly).
True root cause: the app's tap-to-word-lookup competes with the WebView **platform long press**. On
E-ink the press is slow, so the system long press fires first (this device `long_press_timeout`=400 ms) →
`OnLongClickListener` → `handleSentenceLongPress()` → sentence selection → the native selection **action
mode** becomes active → `shouldIgnoreReaderGestureEvent` returns true because
`webView.isNativeSelectionActionModeActive()` → the app's `onTap` (word lookup) is suppressed. So a slow
tap becomes sentence selection (or nothing), never word lookup. Raising the tap window alone does NOT fix
it, because by the time the finger lifts the action mode is already active and blocks `onTap`.
Fix (branch `codex/reader-own-tap-longpress`, uncommitted): the app now OWNS the tap vs long-press
decision with one threshold.
- `SwipePageTouchListener` and `ContinuousScrollTouchListener` each got a long-press `Handler` timer
  (threshold = `readerTapDurationMillis()` = `max(1500 ms, ViewConfiguration.getLongPressTimeout())`); on
  fire → new `onLongPress(x,y)` → `handleSentenceLongPress(x, y)` (that method now takes coords).
- `webView.isLongClickable = false` disables the platform long press so it can't pre-empt the tap and
  shadow it via the action-mode guard.
- The action-mode guard still blocks gestures while a selection is already open (correct), but no longer
  shadows a *fresh* tap.
- CHANGELOG `[Unreleased]` Fixed entry updated to describe this.
Built (debug APK) and `:app:testDebugUnitTest` passes. **On-device E-ink verification still pending**
(device `S101022210032` / S11A-EB1004P was not connected at write time). Key risk to confirm on device:
that `isLongClickable=false` reliably   suppresses WebView native text selection on this WebView build; if
native selection still leaks, the tap stays shadowed and we need stronger suppression (e.g. also consume
`OnLongClickListener`).
- Installed debug APK to the E-ink device `S101022210032` via USB (`adb -s S101022210032 install -r`).
Device was not visible until `adb kill-server && adb start-server` + physical USB reconnect; on first
attach it showed **no serial** — a fresh USB plug + `adb` server restart made it appear as `S101022210032`.
Now the on-device E-ink verification of the `isLongClickable=false` fix is possible.
- **Root-cause correction (confirmed):** `webView.isLongClickable = false` does NOT stop the WebView's native
  long-press text selection — that selection is driven by Chromium's *internal* long-press timer, independent
  of Android `View` `OnLongClickListener`/`isLongClickable` (web search confirms this). So the original
  `shouldIgnoreReaderGestureEvent` guard (`isNativeSelectionActionModeActive()`) was still shadowing slow taps
  on E-ink. **Real fix:** in `app/src/main/assets/hoshi-web/reader/reader.css`, added a `body` rule with
  `-webkit-user-select: none; user-select: none; -webkit-touch-callout: none;` to suppress the native
  selection entirely. Our lookup/sentence selection is JS-driven (`window.hoshiSelection.*`) and never calls
  `getSelection().addRange`; its highlight uses `CSS.highlights` (`::highlight(hoshi-selection)`), so it is
  unaffected by `user-select: none`. This aligns Android with iOS (no native selection menu). Rebuilt debug
  APK and reinstalled to `S101022210032`; **tap-lookup E-ink verification still pending user report**.
