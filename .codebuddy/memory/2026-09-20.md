## 章节内翻页进度不保存（"书签丢失"，只有章节切换才生效）
- 现象：书内翻几页退出再打开，回到章首；但跨章节能记住。用户观察："感觉只对章节才生效"。
- 根因（`ReaderChapterWebView.navigatePage`）：分页模式翻页成功（`paginate()` 返回 `"scrolled"` → `Advanced`）后，进度上报+保存**必须等 `webView.postVisualStateCallback(...).onComplete` 回调**；魅族 Flyme 设备上该回调**永不触发** → `onDisplayedProgress`（DISPLAY_PAGED，0 次）和 `onSaveProgress`（SAVE，0 次）都不被调用，进度既不进 stateHolder 也不落盘。
- 为什么"只对章节生效"：跨章节走 `Limit` → `onLimit()` → `goToNextChapter/goToPreviousChapter` → `saveReaderPosition` → `onSaveBookmark`，**完全不依赖** `postVisualStateCallback`，所以能正常存。
- 修复（`ReaderChapterWebView.kt`）：保留 `postVisualStateCallback` 作快速路径，新增 300ms 兜底 `commitProgressRunnable`（常量 `PAGE_TURN_PROGRESS_FALLBACK_DELAY_MS`），保证进度一定上报+落盘；`onComplete` 参数改名 `completedRequestId` 并与外层 `requestId` 比较（原代码参数遮蔽了外层 requestId）。

## 【更正】上一节根因判断有误 —— 真正根因是 calculateProgress() 返回 null
- 上面写的"`postVisualStateCallback` 永不回调"是**错的**。加日志后实测：`VISUAL_STATE_DONE completed=N expected=N` **15/15 全部匹配**，该回调**正常工作**；`COMMIT_RUN` 兜底也确实执行（stored == requestId，守卫通过）。
- 真凶：`COMMIT_PROGRESS_RAW raw='null'` **15/15** —— `window.hoshiReader.calculateProgress()` 经 `evaluateJavascript` 拿回来的就是 `null`，于是 `ReaderPaginationScripts.doubleResult(...) ?: return` 提前退出 → `onDisplayedProgress`/`onSaveProgress` 都不调用 → 进度既不进 stateHolder 也不落盘。
- `reader-paginated.js` 的 `calculateProgress`（499-537 行）逻辑上只返回数字（`totalChars<=0` 返回 `0`，否则 `exploredChars/totalChars`），所以只能有两种可能：① JS 抛异常；② 算出 `NaN`（`evaluateJavascript` 把 `NaN` 按 JSON 序列化为 `null`）。
- **教训（durable）**：不要凭"回调看起来没触发"就下根因结论；必须把**回调是否触发**、**守卫是否通过**、**原始返回值**三层都打日志，才能区分"没执行"和"执行了但取到空值"。本次就是栽在这——前面两轮都误判成回调问题。
- 诊断结论（`PROGRESS_DIAG`）：`{"ok":0,"err":"TypeError: candidate.getBoundingClientRect is not a function"}` **16/16**，是 **JS 抛异常**，不是 NaN。

## 【再更正】最终采用参考项目实现，而非"二分查找 + Range"补丁
- 用户提示比对参考项目 `D:\My_Project\Hoshi-Reader-Android_demo`。其 `reader-paginated.js`(492-504) / `reader-continuous.js`(352-364) 的 `calculateProgress` 是**简单遍历累加**，**没有** `isFullyBeforeViewport`、不碰 `getBoundingClientRect`：
  `while (node = walker.nextNode()) { var nodeLen=this.countChars(node.textContent); totalChars+=nodeLen; if (nodeLen>0) exploredChars += this.countCharsBeforeViewport(node, X); } return totalChars>0 ? exploredChars/totalChars : 0;`

## 【新 bug】常驻翻译下阅读时"突然跳几句"（分页/连续都有）——待确认
- 现象：翻译常驻（persistent）状态下，读着读着位置突然跳几句；分页与连续滚动模式都出现。
- 机制（已定位到代码，待实机确认）：`ReaderWebView.kt` 的 effect 以 `readerPosition.displayedPosition.progress` 为 key，进度一变就 `delay(350)` → `requestVisibleReaderPageTranslations()` → `applyReaderPageTranslation()` → JS `applyTranslation` 在段落后 `insertAdjacentElement('afterend', block)` 插译文 div → `refreshReaderLayout()`（清 `paginationMetrics` + `warmPaginationMetrics()`）。
- **关键点：`applyTranslation` 插入译文后没有任何位置保持**（`refreshReaderLayout` 只重算分页，不恢复位置）。内容高度变化 → 分页/滚动位置被顶掉 → 跳动。
- 与我刚修的 bug 的关系：修复前进度冻结（`calculateProgress` 抛异常），该 effect 每章只跑一次，译文基本只在第一页出现（CHANGELOG 亦载"AI full-page translation stop after the first page"）；修复后进度正常更新 → 译文被反复请求插入 → 暴露出这个**本来就存在**的位置保持缺陷。即修好了 A，暴露了 B。
- 待确认（决定下一步）：把翻译关掉或切成"长按显示"模式后是否就不跳了。若不跳 → 确认是译文插入导致，修 `applyTranslation` 加锚点位置保持；若仍跳 → 另有原因，需重新排查。
- 实现注意：两个引擎滚动 API 不同。paginated 有 `getScrollContext/getPagePosition/setPagePosition/alignToPage/registerSnapScroll`；continuous **没有** `getPagePosition/setPagePosition`，直接操作 `document.scrollingElement.scrollTop` / `window.scrollY`（参考 `sasayakiScrollPosition`、`showSasayakiMediaStop`）。锚点保持需分模式处理。
- 另注：`createWalker` 的 `isReaderTranslation` 会排除 `.hoshi-reader-translation` 内文本，所以 `calculateProgress()` 不受译文插入影响（进度本身稳定），问题纯在排版位移。

## 【最终】章节内进度不保存 —— 真正修复
- **根因**：`createWalker()` 用 `NodeFilter.SHOW_TEXT`，产出 **Text 节点**；而 `calculateProgress()` 里的 `isFullyBeforeViewport` 直接调 `candidate.getBoundingClientRect()`。**Text 节点没有该方法**（只有 `Element`/`Range` 有）→ 抛 TypeError → `evaluateJavascript` 返回 null → `doubleResult(...) ?: return` 提前退出 → 进度不上报也不落盘。
- **修复（只改 JS，两处）**：`app/src/main/assets/hoshi-web/reader/reader-paginated.js` 与 `reader-continuous.js` 的 `calculateProgress` 中 `isFullyBeforeViewport` 改用 Range 取几何：
  `var range = document.createRange(); range.selectNodeContents(candidate); var rect = range.getBoundingClientRect();`
  （与同文件 `countCharsBeforeViewport` / `warmPaginationMetrics` 既有写法一致。`reader-visual-novel.js` 用 `progressForScreen`，不受影响。）
- **已还原**：此前基于错误诊断在 `ReaderChapterWebView.navigatePage` 加的 300ms 兜底 `commitProgressRunnable`、`PAGE_TURN_PROGRESS_FALLBACK_DELAY_MS` 及全部调试日志已全部撤掉，还原为原始实现。Kotlin 侧最终**无改动**。
- **durable 教训**：
  1. 判"某回调没触发"前，要把**回调触发 / 守卫通过 / 原始返回值**三层都打日志，区分"没执行"与"执行了但取到空值"。

## 朗读翻页后常驻整页翻译不刷新（分页模式）
- 现象：常驻翻译开着，朗读自动翻到下一页后新页面没有翻译（当前页翻译还在、黄色高亮正常）。
- 根因：常驻翻译刷新由 `LaunchedEffect(readerPosition.displayedPosition.progress)`（effect 2042）驱动；朗读翻页走 `advanceToNextReadAloudPage`，它调 `saveDisplayedProgress(calculateProgress())` 写回进度。但 `calculateProgress()` 经 `evaluateJavascript` 取回是 `null`（见上节 NaN/null 根因），`doubleResult(null)` 为 null → `saveDisplayedProgress` 没执行 → `readerPosition.displayedPosition.progress` 不变 → effect 2042 不重跑 → 新页面不被翻译。
- 修复（`ReaderWebView.kt` `advanceToNextReadAloudPage`）：翻页并采集朗读队列后，显式调用 `requestVisibleReaderPageTranslations()`，让新可见页的常驻翻译被请求（缓存重应用 + 新段落入队）。该调用不依赖 `calculateProgress`，直接修好本症状。已 `:app:installDebug` 装到 MEIZU 20。
- 关键关联：本现象的根因和"书签丢失"是同一个 `calculateProgress()` 返回 null；所以 9082dd5 的朗读进度持久化修复目前也是空操作（进度从未落盘）。要彻底修进度持久化，得先修 `calculateProgress()` 返回 null（NaN vs 异常待 `PROGRESS_DIAG` 日志确认）。翻译修复已不依赖它，独立生效。
